# /start-task — issue から PR までの一気通貫フロー

「issue 作成 → デフォルトブランチから作業ブランチ作成 → コミット → プッシュ → PR 作成」
を定型化する。**このスキルの起動をもって、コミット・プッシュの明示的な指示とみなす**
（グローバル CLAUDE.md の「明示的な指示があるまでコミットしない」ルールを満たす）。

## 引数

順不同・省略可。

- **タスクのタイトルまたは概要**（日本語可）— issue タイトルとブランチ名の元にする。
  省略時はワーキングツリーの差分から要約して提案し、ユーザーに確認する。
- `en` — GitHub に投稿する issue / PR 本文を英語にする（デフォルトは日本語）。

## 言語ルール

- issue / PR の本文: 引数指定がなければ**日本語**。
- コミットメッセージ: 常に**英語**。末尾の Co-Authored-By はシステムプロンプトの指定に従う。
- ユーザーへの報告・確認: 常に日本語。

## 手順

### 0. 状態確認と分岐

```bash
git status --short && git branch --show-current && git remote -v
gh repo view --json nameWithOwner,defaultBranchRef
```

- **変更あり（ワーキングツリーに差分がある）** → フル実行（issue → ブランチ → コミット → プッシュ → PR）。
- **変更なし** → issue とブランチの作成まで行い、「実装後にもう一度 /start-task を実行すると
  コミット → プッシュ → PR から続行する」と案内して終了する。
- 現在のブランチがデフォルトブランチでない場合: 既存の作業ブランチ上なら、その旨を報告して
  「このブランチのまま進める / デフォルトから新ブランチを切る」をユーザーに確認する。
- 変更に**無関係なファイルが混ざっていそうな場合**（今回のタスクと関係ないパスの差分）は、
  対象ファイル一覧を提示してどれを含めるかユーザーに確認する。全部が関連していれば確認不要。

### 1. issue 作成

`gh issue create` で作成する。本文の構成:

- **背景** — なぜこの変更が必要か（現状の問題）。
- **対応内容** — 何をするか（箇条書き。差分がある場合は差分から要約）。
- **備考** — 制約・設計判断・後続タスクなど（あれば）。

タイトルは日本語で簡潔に。作成後、issue 番号を控える。

### 2. ブランチ作成

- デフォルトブランチを最新化してから切る: `git switch <default> && git pull`
  （すでに変更がワーキングツリーにある場合、pull がコンフリクトするなら stash せず停止して相談）。
- ブランチ名: `<type>/<kebab-case-slug>`。type は変更内容から選ぶ:
  `feat` / `fix` / `refactor` / `chore` / `docs` / `style` / `test`。
  例: `refactor/footer-fse-blocks`, `chore/studio-sync-workflow`。
- `git checkout -b <branch>`（ワーキングツリーの変更は自動的に持ち越される）。

### 3. コミット

- 対象ファイルを**明示的に** `git add <path>...` する（`git add -A` は使わない）。
- コミットメッセージ（英語）:
  - 1行目: `<type>: <summary>`（conventional commit 風、小文字始まり）。
  - 本文: 変更の背景と何をしたかを 2〜6 行。**なぜ**が分かるように。
  - `Closes #<issue番号>` を本文に入れる（マージ時に issue が自動クローズされる）。
  - 末尾に Co-Authored-By（システムプロンプトの指定どおり）。
- 論理的に独立した変更が複数あればコミットを分けてよい。

### 4. プッシュ

```bash
git push -u origin <branch>
```

### 5. PR 作成

`gh pr create` で作成する。本文の構成:

- 冒頭に `Closes #<issue番号>`。
- **概要** — 1〜3行で何の PR か。
- **変更内容** — ファイル/機能単位の箇条書き。
- **設計上のポイント** — レビュアーが疑問に思いそうな判断の理由（あれば）。
- **動作確認** — チェックリスト形式。実施済みは `[x]`、レビュアー/マージ後に確認すべき項目は `[ ]`。
- 末尾に `🤖 Generated with [Claude Code](https://claude.com/claude-code)`。

### 6. レビュー bot の起動

- **Codex**（`chatgpt-codex-connector`）: リポジトリ側で push 契機の自動レビューが有効なら
  明示的なトリガー操作は不要。有効でないリポジトリ（例: omotegae-project。PR #11 で
  `@codex review` コメント後にしかレビューが付かなかった実績あり）では PR 作成直後に依頼する:
  ```bash
  gh pr comment <PR番号> --body "@codex review"
  ```
  自動レビューが有効かどうか不明な場合は依頼してよい（二重になっても害はない）。
- **Copilot**: 明示的なレビュー依頼が必要。PR 作成直後に依頼する:
  ```bash
  gh pr edit <PR番号> --add-reviewer @copilot
  ```
  - Copilot コードレビュー機能が有効でないリポジトリ（プラン・設定次第）では失敗しうる。
    失敗してもスキル全体は止めず、そのまま次に進めて最終報告に結果（成功/失敗）を含める。
  - GitHub Enterprise Server では `--add-reviewer @copilot` 自体が非対応（`gh pr edit --help`
    に明記）。失敗時のエラーメッセージがこれに該当する場合はその旨を報告する。

### 7. 報告

日本語で簡潔に報告する: issue 番号と URL / ブランチ名 / コミットハッシュ / PR 番号と URL /
Copilot へのレビュー依頼結果（成功したか、失敗した場合は理由）。レビューが付いたら
`/fix-copilot-review <PR番号>` で対応できることを添える。

## 注意事項

- issue・PR の作成は外部公開操作だが、このスキルの起動自体が指示なので個別確認は不要。
  ただし**内容が推測に頼る場合**（タイトル省略時の要約など）は、作成前に本文案を提示して確認する。
- リポジトリに GitHub リモートが無い場合は停止して報告する（`gh repo view` が失敗する）。
- フォーク運用（`upstream` リモートあり）の場合は PR の base を upstream 側にする:
  `gh pr create --repo <upstream-owner/repo>`。
- 既存 issue に紐づけたい場合（引数で `#N` が渡された場合）は issue 作成をスキップして
  その番号を使う。
